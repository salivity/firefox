How Firefox's Sanitizer API Safely Strips Untrusted HTML

This article explores how the Sanitizer API implementation in the Firefox web browser empowers developers to securely handle untrusted HTML strings. By providing a native, browser-level mechanism to parse and strip malicious code before it reaches the Document Object Model (DOM), Firefox helps eliminate Cross-Site Scripting (XSS) vulnerabilities. Below is a breakdown of the dangers of traditional HTML insertion, how the Sanitizer API functions in Firefox, ways to customize its filtering rules, and the security advantages of using a built-in browser API over third-party libraries.

Eliminating the Risks of innerHTML

Web developers frequently need to render user-generated content, such as comments, forum posts, or rich text, directly into a webpage. Traditionally, using properties like Element.innerHTML to insert this content exposed applications to DOM-based Cross-Site Scripting (XSS) attacks. If an untrusted string contained hidden JavaScript, the browser would execute it immediately upon insertion. Firefox's implementation of the Sanitizer API solves this by providing a safe-by-default method to parse and inject HTML without executing underlying scripts.

Native Sanitization with setHTML

At the core of the Sanitizer API in Firefox is the Element.setHTML() method. This method acts as a direct, secure replacement for innerHTML.

When a developer passes an untrusted HTML string into setHTML(), Firefox intercepts the string and parses it into an inert document fragment. Before the fragment is inserted into the active DOM, the browser automatically strips out dangerous elements and attributes. By default, Firefox removes executable tags such as <script>, <object>, and <embed>, as well as malicious inline event handlers like onerror, onload, and onclick. Only safe, clean HTML is rendered on the page.

Protecting Against Mutation XSS (mXSS)

One of the greatest challenges in web security is preventing mutation XSS (mXSS). This vulnerability occurs when an HTML string passes through a third-party sanitizer looking completely safe, but is subsequently altered by the browser's parser during DOM insertion—inadvertently mutating it into executable code.

Because Firefox's Sanitizer API is built directly into its Gecko rendering engine, the sanitizer and the HTML parser are one and the same. The sanitization occurs at the exact moment of parsing. Because there is no discrepancy between how the HTML is sanitized and how the browser understands it, mXSS vectors are effectively neutralized.

Customizing Sanitization Rules

While the default configuration in Firefox is strictly secure and sufficient for most applications, developers often need to adjust rules for specific use cases. Firefox allows developers to instantiate a new Sanitizer() object with custom configurations, which can then be passed into the setHTML() method. Developers can control the output using several straightforward parameters:

  • allowElements: Defines a strict allowlist of the only HTML tags permitted to render. Any tag not on this list is stripped.
  • blockElements: Specifies tags that should be removed while keeping their inner text or child elements intact (for example, removing a <div> wrapper but keeping the text inside it).
  • dropElements: Specifies tags that must be completely eradicated, including all of their inner text and child elements.
  • allowAttributes and dropAttributes: Provides granular control over which attributes (such as class, id, or href) can exist on specific elements or globally across the HTML string.

Performance and Dependency Benefits

Before the introduction of the Sanitizer API, developers had to rely on external JavaScript libraries to clean HTML strings on the client side. By moving this logic into Firefox's native codebase, web applications benefit from significantly faster execution speeds and reduced JavaScript bundle sizes. Furthermore, developers no longer need to manually audit and update third-party sanitization dependencies, as Firefox automatically updates its native sanitization logic alongside routine browser security patches.
